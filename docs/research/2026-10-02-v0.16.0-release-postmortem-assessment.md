# v0.16.0 release post-mortem and process assessment

Date: 2026-10-02. Status: assessment complete; process changes proposed, not implemented.

## Summary

The release process was too expensive and unreliable for this project. It repeatedly made the owner manage the agent, wait for duplicated verification, restart panes, and approve the continuation of an already requested release. The result was days of work before a usable published version. The engineering agent is responsible for those execution and communication failures.

The strongest evidence is the release tail: **six published candidate heads, five failed or cancelled rounds, and no changes to any of the five packaged files during those corrective rounds**. Six test fixture defects and incompatible CI time budgets blocked publication of an unchanged package. Even the final successful path took **76 minutes 55 seconds from develop push to completed publication workflow**, followed by registry verification.

This does not mean every earlier check was unnecessary. The recovery implementation had real concurrency, quota, persistence and rendering defects. An independent package exercise also found a real frozen cached-age display. Those checks earned their cost. The process failed to distinguish that useful work from repeated execution of the same expensive suites, defective qualification tooling, and release bookkeeping.

**Recommended direction:** retain develop/main and trusted npm publication, use one authoritative candidate gate, publish the package that gate verified, and verify a fresh registry installation. Give routine releases a short project-specific procedure. Run extended recovery and fleet qualification when the change requires them, with an explicit budget and acceptance boundary.

## What happened

### Earlier implementation and qualification

The effort began with durable freshness and recovery work. Live observations then exposed additional defects, including snapshot hydration races, query remapping, recovery disclosure, retained-debt pacing, clock skew, transport concurrency and scheduler blocking. That broadened the change beyond a small isolated fix.

Qualification required each personal and work EMU environment to pass an initial 30-minute window and an uninterrupted 24-hour window. Sleep, gaps and candidate-changing repairs invalidated affected evidence. The work environment was on another computer and unavailable locally. These requirements made incident closure expensive; tying publication to their completion also made obtaining a usable update expensive (`docs/plans/2026-09-28-durable-freshness-and-recovery-phases/phase-4.md:16`).

Several qualification failures were in our own preparation:

- A planned quiet migration snapshot was not captured before the owner closed and reopened panes; the retained snapshot was non-atomic (`phase-4-validation.md:11`, in the same phase directory).
- A detached monitor did not remain running. A later invocation reused its stale manifest clock and failed after 49.4 seconds (`phase-4-validation.md:37`).
- An isolated installation changed indirect dependencies. A later installation used the exact locked dependency set (`phase-4-validation.md:154`).
- A ten-pane harness expected 40 subscriptions within 60 seconds even though normal background registration could take 120 seconds (`phase-4-validation.md:269`).
- Disabled Security endpoints and their exact visible notices were not established before dependent runs. Subsequent attempts stopped on endpoint capability and message-matching problems (`phase-4-validation.md:283`, `phase-4-validation.md:305`).

These setup failures should have been exercised offline before spending live account quota or starting a long window. Some later failures also included real internal holds and freshness failures. Correcting a parser or setup deadline could not establish that the application was healthy.

The owner’s Copilot CLI comparison helped identify a useful smaller demand model: keep active Actions updating automatically and make secondary views cached and refreshed on demand. That policy was approved October 1. The previous continuous forty-subscription qualification target then ceased to describe the new default (`docs/plans/2026-09-28-durable-freshness-and-recovery-notes.md:6`).

Architecture diagnosis also came too late. An isolated ten-pane replay eventually reproduced queue timeouts with ample synthetic quota. Increasing queue lifetime still did not meet freshness requirements; bounded concurrent transport was needed. A subsequent replay then exposed a per-pane scheduling barrier that still let a slow background request delay Actions despite spare transport slots. These offline experiments should have preceded repeated long live windows. They identified product mechanisms without requiring disruption of other account workloads; their exact contribution to earlier live incidents remains unmeasured (`docs/plans/2026-09-28-durable-freshness-and-recovery-notes.md:16`, `:24`).

## Findings and causes

### 1. The default release path repeats expensive evidence

The workflow independently runs the same full suites on develop push, the release PR and main push. Publication then explicitly runs npm test and runs it again through prepublishOnly. In the final publisher those two portions took 8m35s and approximately 8m36s respectively.

The package smoke itself took about three seconds. Most publisher time was verification already performed elsewhere. npm documents prepublishOnly as a publish lifecycle hook, so this duplication was discoverable before execution. The publisher also smoke-tests a tarball and then publishes the source directory rather than explicitly consuming that tarball (`.github/workflows/release.yml:94`, `:127`; `package.json:19`; [npm lifecycle documentation](https://docs.npmjs.com/cli/v11/using-npm/scripts/)).

**Correction:** establish one authoritative candidate gate and one tested artifact. After an identical-tree protected merge, perform identity checks and publish that artifact. Remove repeat suite execution from publication. Evidence reuse must include test and harness inputs as well as packaged source; unchanged package bytes alone cannot excuse an unverified test repair.

### 2. Suite names and budgets conceal the actual cost

The documented “fast unit suite” includes a sustained 72-hour virtual recovery oracle. One measured run spent 439.6 of 486.7 seconds in that case, about 90% of the suite. Simulated time did not make this a fast feedback check (`CLAUDE.md:43`; `package.json:21`; `test/sustained-recovery.test.mjs:6`; `docs/release/2026-10-01-v0.16.0.md:232`).

The former ten-minute CI job budget was shorter than one contained test’s fifteen-minute allowance. The publisher’s former fifteen-minute budget could not contain its two observed eight-minute selections plus setup. We discovered these contradictions after remote failures. Raising limits to twenty and forty-five minutes restored feasibility while retaining the waste (`docs/release/2026-10-01-v0.16.0.md:241`).

**Correction:** separate fast behavior checks from extended recovery and exhaustive PTY selections. Keep the extended recovery oracle mandatory for changes to its covered behavior, executed once per accepted candidate. Validate enclosing budgets against measured durations before publication. Recalculating all coverage after every fixture-only change should require a concrete coverage need.

### 3. Test fixtures were unreliable release blockers

| Defect | What the fixture got wrong | Durable correction made |
| --- | --- | --- |
| CI-FIXTURE-01 | Reserved permits before admission, allowing valid admission delay to age them toward expiry. | Acquire fresh permits after admission and test delayed admission explicitly. |
| CI-FIXTURE-02 | Sampled a final Checking frame after successful 217ms recovery. | Assert the ordered recovery and notice-suppression contract. |
| CI-FIXTURE-03 | Allowed five seconds for setup containing a valid five-second phase plus work. | Separate initial readiness from the unchanged signed-webhook delivery deadline. |
| CI-FIXTURE-04 | Treated a bounded busy lock response as missing identity; outer timeout could expire before child timeout. | Bounded transient retries, controlled contention and cleanup after child completion. |
| CI-FIXTURE-05 | Measured start-to-start polling when the product schedules from response completion. | Pair completion and next-start events; retain latency as a regression prerequisite. |
| CI-FIXTURE-06 | Sent keys and quit on fixed sleeps without establishing rows. | Wait for actual Actions and Issues rows, with bounded waits and explicit assertions. |

Sources: `docs/release/2026-10-01-v0.16.0.md:155`, `:165`, `:273`, `:352`, `:425`, `:438`.

The webhook setup failure had occurred in the previous release and had been rerun unchanged. That left a known defect to disrupt the next release. Some hosted failures lacked the original busy reason, response duration or raw terminal capture. Controlled reproductions proved fixture defects, but exact attribution of those hosted events remained inference. One initial webhook reproducer also omitted required budget fields and produced an accidental pass; it was correctly rejected as reproduction evidence (`docs/release/2026-10-01-v0.16.0.md:275`, `:290`, `:359`, `:435`, `:448`).

Local macOS success also did not exercise the Linux terminal runner used by hosted CI. The workflow explicitly exercises GNU util-linux behavior while local full PTY exercises the BSD branch. Node major selections also allowed patch-version differences. Those differences are reasons to test the supported execution contract early, rather than treat each local pass as a guarantee that timing-sensitive hosted fixtures will pass (`.github/workflows/ci.yml:43`, `:138`).

**Correction:** retain the repaired semantic assertions. Adopt a few explicit fixture rules: establish readiness, measure the product’s clock boundary, nest deadlines correctly, await cleanup, and preserve small failure-only diagnostics. Treat a locally demonstrated fixture defect as work to fix before the next hosted round. Do not normalize “rerun until green,” disable the assertions, or enlarge every timeout.

### 4. Incident closure and package release became one moving gate

The original incident deserved real environment proof. The process coupled that proof to releasing a useful update, even with work EMU unavailable and the owner being the primary user. Candidate changes restarted qualification; demand-policy changes made earlier cohort assumptions obsolete.

I should have surfaced the publication-versus-incident decision earlier, with the exact unmeasured behavior and practical options. Instead, repeated explanations of another long window prolonged the owner’s wait. The eventual owner-approved exception was appropriate and explicit; missing evidence stayed open (`docs/release/2026-10-01-v0.16.0.md:115`).

**Correction:** define release eligibility separately from operational incident closure at planning time. Make long live qualification a blocker only for a specific stated release risk. For other releases, use deterministic recovery checks, a bounded canary and honest support limits. A meaningful product change still invalidates affected canary evidence. Do not impose an automatic twenty-four-hour soak on every release.

### 5. Live testing interfered with other account workloads

The owner reported that six candidate processes made at least 28 gh API calls in twenty seconds and that coach-upptime hit the shared personal-token rate limit. This is owner-provided evidence. Initial agent counters did not cover the same intervals or all clients, so they could not establish exact charged-unit attribution.

A later passive sample attributed 85 gh invocations over 65.049 seconds to nine Cirujano controllers, approximately 4,704 calls/hour if sustained. Request counts are not interchangeable with charged primary units, particularly for authenticated conditional responses. Multiple clients were using the account; the experiment needed to account for that before increasing its cohort (`docs/plans/2026-09-28-durable-freshness-and-recovery-notes.md:59`; phase directory `phase-4-validation.md:178`).

The separate archy-upptime and paisaxe-upptime failures were malicious-workflow approval blocks on old Upptime workflows. The owner fixed those. They were not established consequences of candidate polling. Likewise, the proposed pause of nine Cirujano controllers must not be described as an executed pause without evidence.

**Correction:** use synthetic account state and provider fixtures for load and contention tests. Reserve live GitHub checks for a small declared cohort with a quota floor, finite request budget and stop conditions. Prefer passive observation of the existing pane. A credential migration for another application should not become a prerequisite to making gh-glance inexpensive.

### 6. Release policy has multiple conflicting authorities

The managed push policy prohibits a fix-and-repush loop and requires new authorization after local gates. The retained Claude rule instead directs a background agent to fix forward and repush. The native release skill accepts an already supplied version; the retained release command contains unconditional version approval stops. CLAUDE describes PTY as gating main only, while YAML runs it on both branches and PRs.

Sources: `.rpi/rules/push-accountability.md:18`; `.claude/rules/push-accountability.md:19`; `.agents/skills/rpi-release/SKILL.md:8`; `.claude/commands/release.md:81`, `:320`; `CLAUDE.md:35`; `.github/workflows/ci.yml:3`.

The stricter retry policy was real. Some fresh corrective-push approval requests therefore had a contractual basis. The mistake was failing to identify this friction early and obtain a coherent bounded release policy, then repeatedly fragmenting the operation into another “go ahead.” User authorization already covered ordinary production merge, tag and publication; those should not have become repeated decision points.

There is also no project-adapted release playbook at docs/release/release-playbook.md. The native skill points to a 1,541-line generic adoption template. That template itself warns against indiscriminate adoption for small projects and calls for one short procedural authority. We did not implement all of its structural waves, so it would be inaccurate to blame an imaginary platform build. The actual overhead was repeated orientation, interpretation, charter obligations and handoffs (`.agents/skills/rpi-release/SKILL.md:17`, `:41`; its `references/e2e-pro-playbook.md:33`, `:156`).

**Correction:** have one short project release procedure. Keep Claude/Codex adapters thin and consistent. One owner decision should authorize the reviewed version and ordinary release sequence, including a defined allowance for local fixture/workflow corrections followed by a verified corrective push. That allowance is a proposed policy change, not permission to bypass today’s rule. Material product changes, expanded scope, or repeated failures outside that allowance require a new decision.

### 7. Agent orchestration and communication added avoidable work

I gave progress updates around the next gate rather than a reliable end-to-end release path. “Ready” and “nearly done” did not consistently distinguish local preparation, hosted checks, publication and live acceptance. The owner had to ask for status and repeatedly instruct continuation. This made the wait both longer and harder to understand.

Other execution mistakes included late ancestry preparation for strict main protection, excessive manual interpretation of check inventories, and a Sutura monitor assumption that its own head SHA would equal the triggering main SHA. A workflow_run uses the default branch’s commit; its triggering workflow identity must be read from the event. The mistaken filter delayed finalization after main CI was already green. Sutura wrapper success also did not mean repair success: several actual outcomes were gave-up with action_required (`docs/release/2026-10-01-v0.16.0.md:226`, `:149`, `:420`; [GitHub workflow_run semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)).

Ignored generated harness files also entered broad ESLint scanning in the shared checkout and caused unrelated hook failures. Gitignore did not define the lint input set (`package.json:17`). Those diagnostics consumed time without changing the package.

**Correction:** preflight ancestry, runtime, triggers and check names once. Automate required-check completion with correct event identity, explicit terminal outcomes and a deadline. Keep optional repair observers out of the publication critical path. Store executable scratch harnesses outside the product lint scope. Report one current state, one real blocker and the next authorized action; include the remaining pipeline in timing estimates. Stop optional testing once the actual risk and required gate are covered.

### 8. Publication tooling and evidence handling were addressed late

Automatic execution policy rejected gh release create and even gh release view despite supplied user authority. Repeating “go ahead” could not change that tool restriction. CLI was tried; visible browser publication was eventually used. The bridge timeout, stale UI state and fallback added friction. This was a tool-policy constraint, not a failure to notice that gh existed.

The publisher also upgraded to npm@latest during release, adding client drift after local preparation. An npm bin-normalization warning and initial registry 404 then needed investigation. Actual manifest equality, installed bin linkage and CLI execution resolved the warning; the later registry read resolved processing delay. These were not established product failures (`.github/workflows/release.yml:51`; local `publication-remote-checks/github-release-receipt.json`; `published-package/verification.json`, under the October 2 evidence directory).

**Correction:** establish the available publication path early, retain a supported pinned npm client, and implement bounded registry readback. Keep OIDC and provenance. npm supports publishing a tarball, and trusted publication requires an authorized workflow and compatible Node/npm versions; validate the selected artifact publication path before adopting it ([npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/), [trusted publishing](https://docs.npmjs.com/trusted-publishers/)). External tool-policy restrictions can still occur and need a clear fallback, not promises that they cannot recur.

The tracked release report still begins “fresh push authorization required” and ends with main/npm at v0.15.2. Phase validation also has an outdated top summary. Completion truth is dispersed through ignored receipts. Appending history without replacing current status made handoffs unreliable (`docs/release/2026-10-01-v0.16.0.md:3`, `:471`; phase directory `phase-4-validation.md:3`).

**Correction:** maintain one compact current release receipt with candidate, tag, workflow, package integrity, result and accepted limitations. Put historical failures below a clearly dated heading or in linked logs. Derive status from authoritative GitHub/registry readback. Avoid generating a new reporting subsystem.

## What to retain

The following controls had concrete value and should survive simplification:

- Deterministic regressions for conservative accounting, persistence, interruption recovery and active-view freshness.
- A small real-terminal acceptance set for startup, Actions data, tab navigation, cached age, recovery and quit.
- Supported Node compatibility checks; use the complete matrix when the changed behavior warrants it.
- Protected normal promotion, exact version/tag/tree checks and a clean package installation.
- OIDC publication, provenance and registry readback of the actual artifact.
- Independent review for substantial behavior changes. The cached-age charter found a real bug; its useful scenario should become a regression instead of repeating a broad exploratory program every release (`docs/release/2026-10-01-v0.16.0.md:85`).
- Honest unresolved acceptance and preserved failure evidence.

Simplification should reduce repeated operations and unreliable measurement. It should preserve proof of the behavior we intend to ship.

## Lean process alternatives

| Option | Shape | Trade-off |
| --- | --- | --- |
| **A. Keep develop/main; one candidate gate** | Quick integration checks, one required release-PR gate, protected merge, identity verification and OIDC publication of the tested package. | Smallest policy/topology change. Needs careful binding of artifact, tested tree and production merge; required checks must be updated deliberately. |
| B. One protected integration branch | One candidate gate and a verified release tag on the chosen branch. | Removes PR/ancestry states, but changes the established branch contract and is unnecessary for the first improvement. |
| C. Owner-invoked release workflow | One explicit workflow invocation validates a candidate, packs, verifies and publishes through existing npm trust. | Reproducible orchestration, but requires workflow work and a single publication trigger to avoid competing paths. |

**Recommend A first.** Do not add a release service, daemon, capability compiler, new credential system or generic release framework. A small existing-workflow correction and short orchestrating script are sufficient candidates for implementation.

### Proposed routine release sequence

1. **Prepare:** choose the approved version, update notes/version files, review the actual diff, establish change-relevant checks and preflight the publication route. Freeze the candidate after those inputs are settled.
2. **Verify once authoritatively:** fast behavior checks, lint/syntax, relevant terminal acceptance, compatibility and package installation. Include extended recovery or full PTY only for changes that require them. Retain already valid local development evidence instead of repeating every suite just because a release was requested.
3. **Promote and publish:** one required candidate gate, normal protected merge, compare the tested tree/package to production, then publish through the existing OIDC workflow. Do not rerun full suites on identical postmerge contents or during publishing. Never trust an arbitrary PR artifact: bind the artifact to the approved repository, successful run and candidate, and prove merge equality.
4. **Verify delivery and finish:** bounded registry readback, fresh executable version/help check, one completion receipt and task-owned cleanup. Give the owner the installed version and accepted limitations. Check effective Node/npm executable resolution when multiple nvm versions could select different global installs.

Publication identity checks must fail if the production merge changes tested inputs. Such a merge needs new relevant verification. Gate selection must default to broader coverage when uncertain; it must not turn a skipped required behavior into a green check. A simple documented choice for docs-only, ordinary behavior, and coordination/recovery changes is sufficient initially.

These are proposed changes to the current release contracts and branch checks. This assessment does not silently apply them or authorize bypassing current protection.

## Prioritized improvement work

| Priority | Change | Completion evidence |
| --- | --- | --- |
| 1 | Reconcile release/approval rules into one short project procedure. | Both agent adapters and repository guidance point to the same sequence; an approved release proceeds without routine repeated permission stops. |
| 1 | Remove duplicate push/PR/main suite copies and publisher lifecycle duplication. | A dry local trace plus the next authorized release show one authoritative expensive selection and publication of its verified artifact. |
| 1 | Split fast checks from sustained recovery/exhaustive terminal checks. | Commands have measured durations and explicit selection; relevant recovery changes still execute extended coverage once. |
| 1 | Finish fixture reliability and failure diagnostics. | The six corrected failure mechanisms remain covered, readiness/deadlines are explicit, and failed hosted cases retain enough bounded evidence to diagnose them. |
| 2 | Separate bounded operational acceptance from routine publication. | Each release states whether a live window is necessary, why, its cohort/budget, and what remains unmeasured. |
| 2 | Automate the existing sequence and current receipt. | One CLI entry point reports the actual stage/blocker, correlates required runs correctly, verifies delivery, and cleans only owned state. |

Implement these as a small focused change. Do not require another general pre-launch audit or multi-day qualification merely to simplify instructions and remove proven duplicate commands. Behavioral changes to the release tooling still need focused verification, especially artifact identity and fail-closed publication.

Proposed targets, **not yet measured or promised**:

- Routine fast feedback within two minutes.
- Routine patch release from accepted candidate to verified registry installation within fifteen minutes, without a new product defect or provider/tool outage.
- A coordination/recovery release within thirty minutes for automated gates; any necessary live observation has a separately stated duration and purpose.
- One owner release decision for the agreed scope, zero duplicate authoritative full selections, and zero unbounded live experiments.

Measure the next two releases with a few timestamps and counts. If a target fails, identify the specific stage and fix that stage. Avoid building a metrics program around this small tool.

## Accountability and next decision

I should have recognized the duplicate critical path and fragile fixtures sooner, made the release/incident boundary explicit, and carried existing authorization through the normal release sequence. I should have supplied realistic timing, protected other account workloads, and kept one accurate current status. The owner’s repeated requests to finish were clear. The process required too much owner attention after those decisions were already made.

The immediate design decision is whether to adopt Option A and its bounded release authority. The evidence supports it. The next implementation should remove redundant gates and conflicting instructions, preserve the useful product regressions and exact artifact proof, and stop there. A new elaborate methodology would repeat the failure.
