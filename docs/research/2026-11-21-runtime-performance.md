# Where gh-glance spends time and memory

**2026-11-21 · juan294/gh-glance · local develop · 6f1f01ce10a1252eaecf76deea015e4906ca8fa2 · v0.19.4**

How much work happens before the first frame, before the first useful row, during GitHub polling, and when a terminal is idle? Measurements below use the checkout in `/Users/juan/code/gh-glance`, macOS arm64, Node 24.22.3, Ink 7.1.1, React 19.3.1 and installed gh 2.105.0. Dashboard timing used the repository's offline gh fixture. The companion [assessment](2026-11-21-runtime-performance-assessment.md) evaluates the opportunities.

## Startup and the first useful row

A warm restart displayed an Actions row in the first frame in all ten trials. An empty cache made the dashboard's first frame and its first row two different events. The default command took a median 239 ms to show the tab and 4.10 s to show its first row, even with GitHub entirely replaced by a fixture.

**Before the frame.** Standalone startup checks `gh --version` and, for an inferred target, the Git directory. It then discovers remotes and attempts a local warm identity lookup with a one-second bound. React and Ink load after those steps. CLI help and version exit earlier. Headless commands skip the UI imports. A missing CLI or invalid checkout yields a message before entering the alternate screen. Cold identity proof runs after mount, which leaves the dashboard responsive. The host, slug and display-cache resolvers can already resolve a valid explicit target without those URLs. An empty result can trigger discovery again after mount. The doctor command has its own remote inventory. ## GitHub requests and processing

| Surface | What is requested and where the work occurs |
| --- | --- |
| Actions | The default asks for up to 60 workflow runs on a stable REST URL. GitHub omits pull-request expansions. The gh child projects fields with jq before Node receives stdout. The runs normally carry their workflow names. Missing names can trigger one separately admitted conditional catalog request. Resizing leaves the request identity stable. `index.mjs:107`, `index.mjs:1564`, `index.mjs:2071`, `index.mjs:2260`, `index.mjs:2292`. |
| Issues and PRs | GitHub filters open records, orders by update time and supplies counts, cursors and selected fields. The first page is 50 rows. Cursor demand can extend the walk to 150. Later pages receive separate admission. **Conditional reads dominate the recorded REST outcomes.** A read-only snapshot of the local acquisition store on November 21 contained 1,291,008 REST 304s and 17,279 REST 200s. Of those two counters, **98.68% were 304s**. They span this store's accumulated history across tabs and versions. They do not identify a particular endpoint, today's request rate, or the frequency of the missing-workflow-name case. Each authenticated 304 still involves a request. A proper authenticated conditional 304 consumes no GitHub primary quota. The CLI's jq output filter operates on the response. Server-side filters and GraphQL field selections can change what crosses the network. Local counter definitions and transport: `index.mjs:854`, `index.mjs:1047`, `index.mjs:2201`, `index.mjs:14369`, `index.mjs:14425`. [GitHub REST guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) · [GitHub CLI output formatting](https://cli.github.com/manual/gh_help_formatting) · [GraphQL cost model](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api). Rolling documentation and installed gh help checked 2026-11-21.

**Local work after a response.** In a 60-row, 17,494-byte fixture, a conditional Actions hit parsed the saved body and serialized 60 resolved rows even though the batch returned the prior comparison string. The parser still participates in deciding whether workflow names are missing. An unusable cached entity drops its validator so the next admitted request can recover. With 50 Issues in a fixture, the production fetcher called its row mapper 100 times. First-page generation and collection each map the same nodes. Later pages use the collector once. See `index.mjs:2126`, `index.mjs:2178`, `index.mjs:2292`, `index.mjs:2329`, `index.mjs:2561`, `index.mjs:2567` and `index.mjs:18036`.

**Collector difference.** Standalone retains the workflow-name catalog. The collector passes the previous entity validators to the same fetcher and omits the parsed catalog. In three successive admitted fixture polls with one unnamed run and one matching workflow, collector-shaped inputs produced three runs requests and three catalog requests. Passing the catalog forward produced three runs requests and one catalog request. The two eliminated responses were 304s. The name displayed was identical. This exercised the actual fetcher and staged entities with an injected HTTP responder. Collector wiring was source-traced. Runs carrying names require no catalog call in either mode. See `index.mjs:118`, `index.mjs:2071`, `index.mjs:2325`, `index.mjs:10441`, `index.mjs:21162` and `index.mjs:21685`.

**Sharing and recovery.** The local store chooses a producer and publishes a generation for followers. Its one-second inspection normally reads metadata and checks generations before loading rows. A ten-second heartbeat updates liveness. Snapshot reads verify content and retry a racing file replacement. Source admission shares permits and pacing. The UI reports quota waits, retries, unavailable credentials and incomplete Security coverage. Connected clients reuse a local socket or SSH stream, acknowledge a replay on reconnect, and reconnect on a timer. The optional App provider shares token renewal. A 12-subscriber fixture asserts one producer. ## Terminal work and memory

**Visible movement and hidden movement.** The app renders only the visible slice, memoizes rows and enables Ink's incremental output. The spinner trigger scans all loaded Actions rows. Its 200 ms timer updates root state even if Help hides the run. In a current-binary 100×24 PTY with an executing fixture run, a three-second visible interval produced 15 spinner callbacks and 3,915 output bytes. After Help settled, three seconds produced **14 callbacks and zero output bytes**. The session made one Actions request and exited cleanly. Instrumentation counted the 200 ms callbacks and bytes passed to stdout. Separately, 100 local Focus searches over 150 synthetic rows took 0.071 ms median and 0.244 ms p95. **Display cache.** A read-only sample of the current 32-target cache contained 66 tabs and 1,967 rows. Normalized, indented JSON took 1,062,501 bytes. Compact encoding of the same values took 703,517 bytes and decoded identically. The actual loader took a median 3.61 ms across 31 calls on this host. **Retained versus temporary allocations.** The mounted app holds its initial whole-cache result in React state. After a save its mutable references advance to a newly normalized cache. The initial target's checkpoint is still used. In a controlled V8 experiment with 32 synthetic targets × 60 Issues, releasing only the original whole-cache reference while retaining the active target and latest cache freed a median 445 KiB of heap across seven trials. In a separate disk-backed 60-row Actions fixture, one successful acquisition publication serialized the same 35,504-byte snapshot twice, once for capacity accounting and once for persistence. The optional collector created a 16,668-byte buffer for a single-frame snapshot that was sent from its JSON string. These last two figures measure temporary work per fixture publication. ## Scope and handoff

The November 2026 review is based on the local source commit above. Earlier performance work already addressed follower re-sends, fresh/unchanged accounting and unnecessary governor writes. The earlier findings and fixes are recorded in `docs/research/2026-10-31-astra-performance-caching-realtime-review.md:59`. The local Graphify generation dated November 20 supplied leads. File and line references here use the actual checkout.

Three independent read-only investigations covered standalone acquisition, terminal rendering, and optional collector/storage. Each returned source locations, observed costs, counterexamples and focused fixture results. Work used disposable filesystem fixtures, temporary instrumentation, existing dependencies and read-only aggregate counters. All fixture processes exited and their private directories were removed. No project-specific research or assessment overlay was installed. Product, dependency and configuration changes require a separate implementation decision.

Open questions are the frequency of unnamed Actions in real collector installations, how often Help or scrolling hides running jobs, real GitHub transport latency, and the composition of long-session RSS. GitHub server CPU, production end-to-end savings, and hourly savings per user were not measured. Revalidate the checkout, runtime and representative cache occupancy before using these numbers for a change.
