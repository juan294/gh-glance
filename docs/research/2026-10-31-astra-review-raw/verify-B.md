## PC-05 and RT-03: unrelated observer claim blocks all data starts (same defect, verified once)

Both items describe the same check, `startReservation` at index.mjs:6515-6523, and propose the same fix: filter live probe claims by `reservation.costs`. PC-05 also covers the sequential bootstrap in `refreshSharedBudget`. RT-03 limits itself to warm-budget admission.

**Verdict: CONFIRMED for the startReservation barrier. CONFIRMED for the bootstrap sequencing, but code comments document that ordering as deliberate.**
**Severity: medium. Both reports rate it high.**

Evidence (VERIFIED by reading the code):
- index.mjs:6515-6523: `// Any live observer claim defers a start: the claim owns the shared HTTP permit for its window` and then `RATE_RESOURCES.map((resource) => state.probeClaims[resource]).filter(... leaseUntil > at)` with no filter on `reservation.costs`. The quoted evidence matches the code exactly.
- index.mjs:6524-6528: the next check, `unavailableObserver`, is already per resource (`reservation.costs[resource] > 0 && ...outcome !== "healthy"`). So the one check that couples the resources is the probe-claim barrier.
- index.mjs:6026-6029 (claimProbe): drain applies only to work that charges the claimed resource (`reservationCost(reservation, resource, ...) > 0`). Its comment says "an unrelated lane's outstanding request says nothing about this counter".
- index.mjs:3340 `HTTP_MAX_PERMITS = 3`, index.mjs:4077-4100: each request acquires its own permit. The barrier comment says the claim "owns the shared HTTP permit", and that is stale. The exclusive `kind: "bootstrap"` permit (index.mjs:3701, 3716) is for identity resolution at index.mjs:3902. It has nothing to do with governor probe claims.
- index.mjs:5976-5980 (claimProbe comment), index.mjs:6998-7001, and ADR 0003:233-237 all say that a slow observer for one resource must not hold up the other. Plan F07 (docs/plans/2026-09-28-durable-freshness-and-recovery.md:94) says the same.
- Reproduction (VERIFIED by running it): budgets were published and fresh for both resources, the core observer was `healthy`, and a core-only Actions intent (`costs {core:1, graphql:0}`) was scheduled. After `claimProbe(..., "graphql")`, `startReservation` returned `{"status":"waiting","reason":"probe","notBefore":<graphql leaseUntil>}`, a 69,113 ms deferral. The core claim was `null` at that moment.
- Bootstrap: index.mjs:7013-7015 awaits `graphql` and then `core` in sequence. index.mjs:21798-21806 calls `openPollDeadlines` only after the whole `refreshSharedBudget` returns. index.mjs:6998-7009 explains the order on purpose: "Core is refreshed last because its publication is what reopens data admission". The intent is to stop a pane that published a reset from getting a head start over the shared permit.
- Tests: test/governor.test.mjs:2405-2441 asserts `reason === "probe"`, but only for a **core** claim against a core-only reservation (`claimNow` defaults to `"core"`, test/governor.test.mjs:224). This is the same-resource case, so the test does not contradict the defect. No test asserts that a GraphQL claim must block core starts.

Rationale: The barrier is real, and it diverges from ADR 0003's per-resource amendment and from the claimProbe comment. Its stated justification (a single permit) no longer matches the 3-permit pool. Impact is bounded latency, not a stall. The callers (index.mjs:21544-21551 and 21207-21215) re-arm the data wake. Liveness polling runs every ≤5 s (index.mjs:21751-21754), so a deferred start retries soon after the claim is published or failed. The delay therefore lasts as long as the GraphQL claim: the drain of graphql-charging reservations (≤30 s, `GOVERNOR_PROBE_DRAIN_MS`, index.mjs:4364), plus the observer call (≤30 s, `GH_TIMEOUT_MS`, index.mjs:178), plus transitions. A fast observer adds about one request round trip each cycle (`BUDGET_PROBE_MS = 60_000`, index.mjs:2743). A slow or timing-out GraphQL observer can add 30-60 s to Actions freshness each time it runs. A failing observer releases its claim through `failProbeClaim`, so failure does not wedge core work, and F07's literal "failure" wording is mostly met. Its "slow" wording in the ADR is not. That is why I rate it medium, not high.

Proposal soundness: RT-03's narrow version, filtering `liveClaim` by `reservation.costs[resource] > 0` in startReservation only, is sound and safe. Same-resource drain and debt snapshots stay intact. Core starts after a core reset still need a fresh core budget in the new epoch (index.mjs:6531-6537 cancels when `at >= budget.resetMs` or the epoch differs), so the reset choreography is preserved. Transport concurrency remains bounded by the 3 FIFO permits, the 250 ms gap and the host cooldown. One side effect: the GraphQL observer may now queue behind data requests for a permit. Renewal (index.mjs:7117-7130) covers that, but a test should check that the observer still completes within its lease under a full permit pool. PC-05's broader proposal to refactor `refreshSharedBudget` and bootstrap ordering conflicts with a documented ordering choice (index.mjs:6998-7009) and is riskier. Do the startReservation filter first, then measure.

## RT-02: secondary throttles become primary-reset blocks; paused circuit has no runtime recovery

**Verdict: CONFIRMED for both parts.**
**Severity: high.** The paused circuit is a persistent, host-wide wedge with no in-app exit. The misclassification part alone would be medium.

Part 1, secondary throttle published as a block until primary reset (VERIFIED by static trace):
- index.mjs:410-411 `isRateLimited`: `/rate limit|secondary rate|API rate limit/i`. GitHub's secondary message ("exceeded a secondary rate limit") matches.
- index.mjs:483 `classify` returns `"rate-limited"` for it. No structured `classifyThrottle` verdict is consulted on this path.
- index.mjs:20155-20168 (`App.commit`): for each resource the tab costs, it pushes `{ resetMs: snapshot.value?.budgets?.[resource]?.resetMs }`, which is the sampled **primary** reset. index.mjs:19982-19989 does the same for core when Security's `rateLimited` is set. That flag comes from index.mjs:7502 (`parts.some(part => part.verdict === "rate-limited")`).
- These blocks go through `handleRateLimitBlocks` (index.mjs:20731) to `recordResourceBlock(currentScope, name, resetMs, "rate-limit")` (index.mjs:20710), which sets `budget.blockUntil = resetMs` (index.mjs:6880) in the shared governor. Every pane is affected.
- The block survives later observations in the same epoch: index.mjs:6142-6146 (`preserveBlock = !clearProvenBlock || !epochChanged`). A manual probe cannot pull core observation forward either: index.mjs:6389-6391 (`heldThroughReset` keeps `nextAt` ≥ `blockUntil + grace`). `startReservation` refuses while `blockUntil > at` (index.mjs:6535).
- The transport layer meanwhile classifies the same response correctly as secondary and applies only a host cooldown (index.mjs:4248-4261, `classifyThrottle` index.mjs:4158-4189). ADR 0003:257-262 says: "Primary exhaustion holds only its own resource until that resource's reset. A confirmed secondary limit or a generic 429 holds the account". The commit path contradicts that.

Part 2, the paused circuit (VERIFIED):
- index.mjs:4216-4217 sets `paused: attempts >= THROTTLE_PAUSE_AFTER` (5, index.mjs:4147). Each errored permit release increments the counter (index.mjs:4254-4261). With 3 concurrent permits, three in-flight requests hit by one throttle event each count, so 5 can be reached in about two throttle rounds.
- When paused, `acquireIdentityHttpPermit` refuses every request (index.mjs:4081-4083), and so does `claimIdentityBootstrap` (index.mjs:3700). That covers observers, data and identity bootstrap.
- The ladder clears only when a request completes without an error (index.mjs:4264-4266). While paused, no request can start, so this cannot happen.
- `retryThrottledTransport` (index.mjs:4277-4285) is the only code that clears `paused`. Its only reference outside its definition is the export list (index.mjs:22645). A grep of index.mjs for `throttle.paused`, `paused: false` and `retryThrottledTransport` found no other writer. A grep of test/ found no caller of `retryThrottledTransport`. No code removes `state.hosts[...]` (index.mjs:3461, 3546-3557 only migrate/prune waiters). The state lives in the persistent identity registry, so the pause survives restarts.
- The UI tells the user to press r (index.mjs:16363, and index.mjs:4301 "refresh to retry"), but `r` does not reach the transport circuit. ADR 0003:270-273 and plan table row "Secondary hold / repeated-secondary circuit" (plan:115-116) promise an explicit retry or a reset-triggered recovery.

Rationale: Both mechanisms are traced end to end. For part 1, take a 60 s secondary hold with N minutes left in the primary window. Affected resources stay blocked for all panes for about N minutes, and neither observation nor `r` lifts the block before the reset. For part 2, once tripped, the host transport stays paused until someone edits the registry file by hand.

Proposal soundness: The direction is sound. The model's own caution is correct and load-bearing: `retryThrottledTransport` sets `cooldownUntil = Math.min(cooldownUntil, now())` (index.mjs:4282). Wiring it to `r` as it stands would shorten a server-supplied Retry-After, which violates ADR 0003:262-266. The fix should clear `paused` and `attempts` but keep `cooldownUntil`. It also needs a single-pane election, because `r` in one pane unpauses the shared host for all panes and collectors. For part 1, the fallback matters. When structured evidence is missing (stderr only, "API rate limit exceeded" with no headers), `classifyThrottle` returns `none`, so the existing primary block must stay for unclassified primary text. Only evidence classified as secondary should skip the resource block.

## PC-08: governor inspections rewrite the ledger when nothing changed

**Verdict: PARTIAL.** The no-op rewrite is real. The claim that it makes "diagnostic projections appear changed" is not supported: I found no consumer of the governor's top-level `revision`.
**Severity: low.**

Evidence:
- index.mjs:5747-5791 `mutateGovernor`: after any non-failing mutator it normalizes and calls `commitGovernorMigration` (index.mjs:5787-5789). With no migration, that calls `writeGovernorState` (index.mjs:5411). `writeGovernorState` increments `revision` (index.mjs:5422), writes a temp file (index.mjs:5432) and renames it (index.mjs:5436). There is no dirty check. By contrast, `withIdentityRegistry` skips identical writes (index.mjs:3596, `if (JSON.stringify(state) === before) return result;`).
- `claimProbe` waiting paths (index.mjs:5986-5988, 6013) and `readIntentDecision` (index.mjs:6453-6482) return successful values through that path.
- Reproduction (VERIFIED by running it): a waiting `claimProbe` moved revision 9 to 10 with a new inode. Two consecutive `readIntentDecision` calls on an unchanged scheduled reservation moved revision 10 to 11 to 12 with a new inode. Ledger content was byte-identical apart from `revision` (3,247 bytes in the sandbox). `inspectGovernor` did not write (revision 13 to 13).
- Callers: `readIntentDecision` runs once per pending item on each data wake (index.mjs:21508). The liveness wake runs at `min(refreshMs, 5000)` (index.mjs:21751-21754). `claimProbe` waiting runs at most twice per resource per control cycle (index.mjs:7045, 7070).
- `revision` consumers: grepping `.revision` shows only the overflow guard (index.mjs:5419) and normalization (index.mjs:4728-4729). The other hits are debt revisions or other registries (index.mjs:8xxx). Panes poll on timers rather than watching the file, so no-op writes do not cause wake ping-pong (INFERRED from the wake structure at index.mjs:21735-21775; I did not do an exhaustive search for fs watchers).

Rationale: The cost is one full serialize, write and rename per no-op under the governor lock. That makes the lock hold time longer for other panes, and the cost scales with ledger size (cap 2 MiB, index.mjs:4354). Typical ledgers are a few KB, and the frequency is a few calls per pane every few seconds. This is an efficiency problem, not a correctness one. The revision bump has no observable effect that I could find.

Proposal soundness: Sound if the comparison covers the post-maintenance state. `mutateGovernor` runs `reconcileBootDebt`, `compactGovernorReceipts`, `compactQuiescentDebtGroups` and normalization before and after the mutator. Comparing serialized normalized state against the loaded bytes (or a pre-mutation snapshot) catches all of these, as `withIdentityRegistry` does. Keep the forced write on migration. Do not skip writes on paths that return `{ ok:false, write:true }`. There is no quota or rate-limit interaction.
