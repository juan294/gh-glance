## Design choices

- **Keep the runtime, transport and polling policy.** The research measured a 239 ms median first frame and a 4.10 s median first cold row on the default fixture. Four follow-up rows appeared 57–77 ms after the fixture invocation. Changing first-demand timing can affect waiting before admission. Increasing request concurrency or relaxing the lease phase would change the fairness contract. See `index.mjs:3307`, `index.mjs:21758`, `docs/decisions/0003-file-backed-api-coordination.md:107`.
- **Keep the disk and wire formats readable by existing versions.** Compact JSON changes whitespace. The transaction-local snapshot optimization reuses identical bytes. The collector continues to emit the same single or chunked snapshot. Only the two changed GraphQL documents receive new query identities, so old and new panes can coexist. See `index.mjs:9525`, `index.mjs:14250`, `index.mjs:14856`, `docs/decisions/0004-quota-and-acquisition-identities.md:159`.
- **Use operation counts for deterministic improvements and paired timings for latency.** A dormant Help screen already wrote zero bytes while firing 14 callbacks. Catalog reuse in the fetcher fixture avoided two conditional requests across three polls. The 33.8% cache reduction and 445 KiB controlled heap observation describe populated fixtures. Treat each as a baseline to reproduce at the relevant layer. Absolute RSS, GitHub quota savings and production latency have no established improvement target. See `docs/research/2026-11-21-runtime-performance.md:35` and `docs/research/2026-11-21-runtime-performance-assessment.md:19`.
- Prefer small changes in `index.mjs` and existing Node/PTY suites. Use local fixture instrumentation for measuring bytes, calls, timers and retaining paths. Product flags, production profiling, CI routing and release workflow changes are outside the requested runtime work.

## Implementation and acceptance

Use an isolated local worktree or temporary branch for each authorized phase. One owner integrates. All five phases modify `index.mjs`, and the corresponding fixture changes must agree with its behavior. There are no independent implementation units with disjoint file ownership to mark batch-eligible. The implementer writes focused failing regressions, makes the change, obtains independent review, repairs, simplifies and verifies. Stop at each phase for acceptance under the installed workflow.

**Automated.** For each implemented phase, run `npm run lint`, `node --check index.mjs` and `npm test` sequentially. Run `npm run test:efficiency` when the phase touches acquisition, collector behavior, scheduling or efficiency behavior, and `npm run test:pty` for rendering or terminal lifecycle. The phase files name the applicable commands and targeted red/green oracles. Existing tests already run by a required suite count as evidence. Capture exit results, platform, Node version and tested commit. Use separate disposable fixture roots except where intentional sharing is under test. Reuse the repository's standard capture teardown and synthetic gh transport. See `AGENTS.md:92`, `package.json:16`, `test/pty/capture.mjs:463`.

**Manual.** The changes expose no new user controls. PTY assertions exercise keyboard, resize, restart and reconnect. No owner-operated verification is required. Keep local timing/heap samples with phase evidence and distinguish them from deterministic pass/fail checks.

## Stuck states and recovery

| Affected user or operation | Visible behavior and recovery | Oracle |
| --- | --- | --- |
| Startup fails local preflight or cannot infer the target | Existing command diagnostic before alternate-screen entry. Correct the target/install gh and rerun. A slow credential helper still allows mount, with later safe cache hydration. | Phase 1 exercises missing gh, ambiguous remotes, delayed credentials and corrected relaunch. |
| Idle or covered running row | Settled display parks. Scroll, resize, leave Help or start a visible check and animation resumes automatically. | Phase 2 counts timer firings and terminal output through both transitions. |
| Cache unavailable, corrupt, busy or superseded | Cold live acquisition remains available. Cached known-good rows survive failed source reads. A pending latest write survives failure until a later flush/dispose. Width preferences retain their existing save feedback. | Phase 2 checks failure → retry → warm restart, peer edits, reentrant/superseding writes and SSH checkpoints. |
| Catalog missing/denied, invalid conditional entity or stale collector binding | Run data stays usable where available. A missing cached entity drops its validator for a later unconditional request. A new binding discards the old catalog. | Phase 3 verifies failed/renewed catalog, following request headers, and delayed old-binding discard. |
| GraphQL page denied or older query identity exists | A first-page failure follows the existing error path and keeps last-good rows. A denied later page leaves the partial walk marked incomplete. Later demand can fill it. A changed document starts its own query with the supported display cache available. | Phase 3 checks partial walk → later successful walk and mixed-version access. |
| Disk capacity, lock failure, stale observation or collector transfer interrupted | Existing wait/disconnect/freshness indications remain. A later admissible publication/reconnect supplies a verified snapshot. Diagnostic data ages out or recovers on a later observation. | Phase 4 checks rollback followed by successful retry, monotonic projection recovery, reconnect and chunk assembly. |
| Initial demand arrives during a hold or simultaneous startup | Existing wait state is shown. Ordinary next wake handles recovery after valid evidence. A granted request begins at or after its permitted time. | Phase 5 uses held → healthy, expired-slot retry and same-target multi-pane cases. |
