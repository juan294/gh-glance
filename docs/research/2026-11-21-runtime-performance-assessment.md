# Low-risk performance opportunities in gh-glance

**Decision brief · 2026-11-21 · juan294/gh-glance · develop at 6f1f01ce10a1252eaecf76deea015e4906ca8fa2 · v0.19.4**

Keep the current gh, React and Ink architecture. Start with three small changes: skip redundant Git discovery for an explicit repository, stop animating rows the user cannot see, and reuse the collector's workflow catalog. Each removes work at its source and can be verified by counting processes, callbacks or requests. For many-repository users, the display cache offers a measured reduction in repeated disk and CPU work. The [runtime research](2026-11-21-runtime-performance.md) gives the workload, measurements and source provenance.

The evaluation favors visible latency, fewer actual GitHub calls, lower terminal CPU or smaller retained memory. It also weighs frequency, implementation size and whether a change affects freshness, supported hosts, cache compatibility or behavior across panes.

## For a workstation with many repositories

**Use compact JSON for the display cache and check object identity before comparing serialized values.** On the local 32-target cache, compact encoding reduced each full write from 1,062,501 to 703,517 bytes, a **33.8% reduction**. Adding an identity check brought the median in-memory three-way merge for a one-target timestamp change from **2.85 to 1.33 ms**. They address different parts of the same save. The current loader took only 3.61 ms even on this cache, so these numbers principally support smaller writes and less synchronous work under lock. The file is documented as UI-owned recovery data. Keep deep comparison for independently decoded objects, support existing indented files, and preserve concurrent updates to different tabs and targets. A larger storage redesign would need a workload where these smaller changes prove inadequate. `index.mjs:13718`, `index.mjs:13745`, `index.mjs:14250`, `index.mjs:14267`, `index.mjs:14297`, `README.md:746`, `test/runtime-remediation.test.mjs:208`.

**Retain the initial target's checkpoint and let the superseded whole-cache graph go.** A controlled 32-target experiment reclaimed about 445 KiB of JS heap after a successful save. Both live and persisted references must still advance together, and SSH recovery still uses the initial target's source timestamps. This is a bounded memory improvement for populated caches. A material change to long-running process RSS remains unproven. `index.mjs:13781`, `index.mjs:14312`, `index.mjs:19527`, `index.mjs:21491`.

## The larger startup and memory questions

**Cold first data is a scheduling question.** The four instrumented reservations placed first Actions data 1.47–3.23 seconds into the future. GitHub could have returned instantly and the app would still have waited. Three further traces also found a one-second timer for the *initial* data wake. The active tab's due time had already passed when it reached the same helper that slows repeated overdue retries. If cold starts are the product priority, the narrow experiment is to submit the first demand promptly while retaining the original permitted request time, cross-pane sharing and ordinary retry delay. Compare first demand, permitted start and first fresh row across **matched early and late slots**, for one pane and simultaneous launches. A later permitted slot can absorb the entire saving. Changing the five-second phase policy itself would change multi-pane behavior and needs separate evidence. `index.mjs:21758`, `index.mjs:21775`, `index.mjs:22012`, `index.mjs:22903`, `index.mjs:3307`, `test/governor.test.mjs:1023`, `test/pty/governor.test.mjs:487`.

**Keep the runtime and transport.** The separate-process import measurements put React and Ink at 88.8 MiB RSS, and importing the entire app at 93.5 MiB. At this sample size there is little evidence that splitting the application file for its own sake would change the memory profile appreciably. A renderer replacement or a long-lived shared UI service would take on keyboard, resize, accessibility, lifecycle and isolation behavior. Existing viewport rendering, incremental terminal writes and memoized local search already cover much of that ground. A long-session heap and physical-footprint profile on a busy pane would be needed to justify a larger memory intervention. `index.mjs:12750`, `index.mjs:19834`, `index.mjs:23114`, `index.mjs:23601`, `docs/decisions/0002-own-the-terminal-lifecycle.md:21`.

The local store's 98.68% conditional-hit share leaves little body transfer to remove on those particular requests. A 304 still costs a round trip. Increasing polling intervals exchanges freshness for fewer requests, and bundling inactive tabs into a query adds work on the default on-demand path. The optional collector already offers shared acquisition, an SSH transport and webhook reconciliation where deployment warrants it. A transport replacement would need evidence that gh process launch or connection setup dominates a representative live workload after admission. GitHub documents the distinction between conditional REST quota and GraphQL query cost. `index.mjs:1564`, `index.mjs:16066`, `index.mjs:10539`, `index.mjs:11360`, `index.mjs:7841`, `docs/decisions/0001-keep-the-gh-cli-data-layer.md:29`. [GitHub REST guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) · [GitHub GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api).

**Handoff.** This assessment uses the local checkout, fixtures, source versions and limits recorded in the companion research. There was no project-specific overlay. The first choices are ready for an owner decision. Their proposed gains are operation counts or isolated component measurements. Product-level speed, hourly traffic and long-session memory effects require measurements on an implementation. No product implementation or publication was part of this work.
