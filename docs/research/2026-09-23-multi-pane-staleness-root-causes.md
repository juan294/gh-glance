# Research: multi-pane staleness in gh-glance 0.15.1

Date: 2026-09-23. Scope: the three screenshots show `Stale stale 99h59m`, `15h49m`, and `3h36m`; the first displayed age is capped by code and can represent any longer interval. This document records current code and live observations, then distinguishes confirmed cause from unresolved earlier delays. The installed CLI is 0.15.1 and its source matches this `develop` checkout. [Evidence](2026-09-23-live-staleness-evidence.md:8), [display cap](../../index.mjs:17404)

## Confirmed shared stop

The five panes already running at 07:54 stopped updating the same acquisition store. Its lock is an empty 0600 file last modified at 07:54:59 CEST, the store's last write was 07:54:54, and no process had the lock open when inspected. The metadata retained 20 subscriptions whose heartbeats expired around 07:55. A sixth pane started later and could not join that store. [Evidence](2026-09-23-live-staleness-evidence.md:13)

Every local pane resolves the same `coordination-v2/acquisition.json` path. `withAcquisitionStore` creates its lock with an exclusive write; when it meets an existing lock whose owner record cannot be read, it returns `busy`. It can reclaim a complete lock owned by a dead PID, but it has no age-based path for an empty or malformed lock. Subscription, heartbeat, refresh, publication, and metrics operations transact through this store. [Shared path](../../index.mjs:12182), [lock behavior](../../index.mjs:12947), [transaction seam](../../index.mjs:13098), [heartbeat](../../index.mjs:13163), [refresh](../../index.mjs:13550)

The failure reproduces without GitHub or the live store: an isolated acquisition engine given a 60-second-old empty lock returned `{ok:false,reason:"busy"}`. The existing governor lock implements age-bounded recovery for an unreadable record, and its unit test covers both empty and partial records; the acquisition lock uses a separate implementation. [Reproduction](2026-09-23-live-staleness-evidence.md:29), [governor recovery](../../index.mjs:4238), [governor test](../../test/governor.test.mjs:2597), [acquisition lock](../../index.mjs:12952)

The exact event that created the empty file is unknown. The acquisition writer's single `writeFileSync(..., flag:"wx")` can leave a file after an interrupted or failed write; the saved file proves the outcome, not whether the trigger was a write error, process exit, or another filesystem event. The disk had 31 GiB available when checked, which does not establish its free space at 07:54. [Writer](../../index.mjs:12959), [evidence](2026-09-23-live-staleness-evidence.md:15)

## Earlier stale intervals are distinct

The empty lock is not a complete explanation for every displayed age. Before 07:54, the saved Archy Actions query last succeeded at 19:37 CEST on September 22, and Sutura Actions at 00:36 CEST on September 23. Each acquired a new claim seconds later. Both claims still had `started:false` when the store froze hours later. Fifteen claims across the store had that state. The cropped screenshots do not identify their repositories, so these records cannot be assigned to a particular screenshot. [Evidence](2026-09-23-live-staleness-evidence.md:23)

The acquisition engine treats a claimed query as follower work unless the claim has expired **and** its owner PID is dead. Its heartbeat extends the lease of any claim owned by the live process, whether or not transport has started. A live process can therefore keep an unstarted claim occupied while governor admission waits. The saved state proves long-lived unstarted claims; it does not prove what first prevented their reservations from starting or why pending work did not clear. [Claim decision](../../index.mjs:13568), [heartbeat extension](../../index.mjs:13177), [admission and pending path](../../index.mjs:16849), [resume path](../../index.mjs:16993)

The runtime has a possible additional gate: governor observations are maintained for core and GraphQL separately, but `governorProtocolReady` requires both observers healthy and both budget snapshots fresh before any resource's data scheduling opens. Thus a persistent observer problem in one resource can hold requests for the other, independent of that resource's spendable budget. The current live state does not show that this caused the older claims. [Protocol](../../index.mjs:13970), [per-resource data check](../../index.mjs:13998), [startup gate](../../index.mjs:17214), [pending request gate](../../index.mjs:16808)

`runDataWake` returns without rearming when governor inspection fails, while `controlWake` and bootstrap await identity and budget operations without a local catch/finally around their final wake scheduling. These are code paths to distinguish from a held claim in a future trace; no thrown error or lost wake was observed in this session. [Data wake](../../index.mjs:17053), [control wake](../../index.mjs:17124), [bootstrap](../../index.mjs:17193)

## What the current evidence rules out

Current primary quota exhaustion does not explain the all-pane freeze: the live governor had thousands of core and GraphQL units above its 1,000-unit reserves, while the acquisition store stopped writing and the quota files continued updating. Authentication and the GitHub Actions endpoint were working in independent `gh` checks. These checks do not rule out earlier transient API or identity failures. [Live budget and direct call](2026-09-23-live-staleness-evidence.md:17), [reserve and admission](../../index.mjs:13998)

Current acquisition capacity also does not explain the freeze: the saved store had 20 subscriptions and 36 queries, below the 128-subscription and 512-entity caps. Its live target limit is 32. The installed source matched `develop`, so a local/installed code difference did not explain the reproduced empty-lock behavior. [Counts](2026-09-23-live-staleness-evidence.md:16), [version](2026-09-23-live-staleness-evidence.md:8), [caps](../../index.mjs:12175)

## Why the interface gave little diagnosis

The footer composes a semantic `Stale` status and a separate `stale <duration>` detail, which produces `Stale stale ...`. The age is based on the last successful source observation, not row change; the displayed age is capped at 99h59m. The text conveys age but not the failed gate. [Status](../../index.mjs:14630), [age](../../index.mjs:17383), [cap](../../index.mjs:17404)

An acquisition error sets a coordination decision, but a subsequent healthy budget status can replace that decision. The stale conversion can then replace `Watching` or `Shared` with `Stale`. This explains why the footer alone cannot identify the acquisition lock or the older unstarted claim. [Acquisition error](../../index.mjs:16849), [budget status](../../index.mjs:15788), [stale conversion](../../index.mjs:17408)

`--doctor --probe` reported the acquisition section as `healthy` with zero active subscribers while the empty lock was present. It reads and normalizes acquisition metadata without claiming the lock; the diagnostic status is hard-coded `healthy` when that metadata parses, and expired subscribers disappear from the active count. The current doctor report therefore did not test whether acquisition writes could proceed. [Observed report](2026-09-23-live-staleness-evidence.md:17), [metadata read](../../index.mjs:12832), [diagnostic status](../../index.mjs:12370), [doctor call](../../index.mjs:9993)

## Coverage and evidence limits

The sustained-hour acceptance uses an injected clock, 100 ms synthetic response latency, and subscribes each repository to Actions only. The changed-row latency samples come from two injected Actions changes on one repository; per-repository progress assertions count successes but do not bound the longest gap between them. Its validation report labels the real-account quota smoke optional. These checks do not establish mixed-tab, multi-day freshness under live locks and admission. [Workload](../../test/fixtures/workloads/multi-instance-v1.json:18), [Actions subscription](../../scripts/measure-efficiency.mjs:650), [latency sampling](../../scripts/measure-efficiency.mjs:667), [progress assertion](../../test/efficiency.test.mjs:84), [validation boundary](../plans/2026-09-05-multi-instance-efficiency-phases/phase-12-validation.md:42)

The real-process pacing soak lasts 40 seconds and explicitly does not detect a missing return of unused pacing credit. Existing acquisition tests cover busy publication with a valid owner lock that the test manually removes; the aged empty acquisition lock was absent from that path. [Pacing soak](../../test/pty/pacing-credit.test.mjs:24), [stated limit](../../test/pty/pacing-credit.test.mjs:149), [acquisition test](../../test/acquisition.test.mjs:1217)

The confirmed cause of the current common freeze is the orphaned empty acquisition lock. The cause of the earlier hours-long unstarted claims remains unproven because the saved state contains claim outcomes, not the corresponding historical admission decisions or request traces.
