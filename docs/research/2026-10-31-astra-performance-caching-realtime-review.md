## Summary

The core design holds: the verifiers and the model both found the gh transport, bounded queries, conditional REST, shared acquisition and the governor's admission model sound and not worth replacing. The defects concentrate in three places:

1. **Collector with several targets on one provider** (PC-01, PC-02): targets share one mutable repository scope and one Security negative cache, so one repository's rows or "not enabled" notes can appear under another. This applies only when one collector serves two or more repositories through the same provider (INFERRED: whether the owner's own setup does this was not checked).
2. **Rate-limit recovery** (RT-02): a secondary throttle is treated as primary exhaustion and blocks the resource until the hourly reset, and after five throttles the transport pauses with no runtime path that clears it, while the UI still says "Press r".
3. **Freshness bookkeeping** (RT-01, RT-06, RT-07, PC-06/RT-05, RT-04): the collector never sees GraphQL snapshots as unchanged (so it polls at the floor instead of the quiet cadence), some paths stamp cached data as a new observation, and reconnect or idle states show the wrong connection status or a frozen clock.

## Suggested fix order

1. **PC-01**, then **PC-02** (same code area; PC-02's repository-scoped key needs PC-01's immutable per-target binding). Add the two-target, one-provider test that the suite lacks. Keep the credential coordinator and quota ledger shared per provider; only the operation scope becomes per target.
2. **RT-02**: carry `classifyThrottle`'s structured result through `fetchAlertSource`/`fetchSecurity` and `App.commit`, publish a primary block only for primary exhaustion, and add a single durable recovery path for `paused` that never starts before an outstanding server deadline.
3. **RT-01 and RT-06** together: one validated comparison representation shared by fetchers, `normalizeAcquisitionSnapshot`, `pollResultTransition` and adoption (include completeness and coverage notes; exclude timestamps). Null `rawRef` on adoption of changed rows; do not copy `snapshot.raw` until RT-01 is fixed. This is the main request-volume win.
4. **RT-07**: report whether any accessible Security source produced a real 200/304 observation; do not advance success time or resolve webhook waiters on an all-backoff batch. Consider also clearing capability backoff when a security webhook arrives (at most 3 REST calls per delivery; verifier suggestion).
5. **PC-05/RT-03**: filter the observer-claim check in `startReservation` by the reservation's resources. Leave the bootstrap order alone.
6. **PC-06/RT-05** and **RT-04**: let an equal-generation replay acknowledge the connection (still rejecting older generations and epochs), and give the App a display clock independent of acquisition.
7. **PC-04**, then the optimizations **PC-07** and **PC-08**.

All proposals were judged sound by the verifiers, and none needs extra GitHub requests except PC-02, which restores Security requests that are currently suppressed by mistake (and lowers volume overall by letting each repository's ladder climb).

## Checked and found sound (model and verifiers)

The gh CLI transport and bounded GraphQL queries, conditional REST with validators, shared acquisition between panes, the governor's admission and per-resource draining, and the deliberate on-demand default (Issues, PRs and Security refresh only when opened, refreshed or updated by a subscriber). The model put default staleness at 5 s for running CI, 30 s for quiet Actions, Issues and PRs, 60 s for quiet Security, and 120 or 300 s for inactive tabs (index.mjs:15816-15836); these are scheduling delays after completion, not end-to-end guarantees, and there is no finite bound during provider, authentication, quota or coordination holds.
